01Executive summary

This record describes how the IPCOR national prostate-cancer registry was standardised to the OMOP Common Data Model, version 5.4. It is written so the IPCOR team can keep it, circulate it for sign-off, and share it further at their discretion.

The IPCOR extract arrives as five source files in the registry's own format, with its own field names and coded values, and no pre-existing standard vocabulary. The task was therefore twofold: decide, for every field and every coded answer, which standard OMOP concept represents it, and then transform the data into the CDM tables so it can be queried and compared across sites.

The mapping followed the standard OHDSI toolchain. The source was profiled with WhiteRabbit; the table-by-table ETL design was authored in Rabbit-in-a-Hat; each field was mapped to a standard concept found in Athena; each categorical value was mapped in Usagi and exported as a source-to-concept map; and the result was validated with the OHDSI Data Quality Dashboard. Because IPCOR has no ontology of its own, every concept was sourced from Athena and reviewed by hand.

Alongside the mapping, a set of tools was built so the pipeline runs without touching code: a one-click Docker appliance that turns the raw CSVs into an OMOP database on the user's own machine, a research dashboard over the built data, and an optional analysis workbench (RStudio Server and JupyterLab) in which a collaborator can run an OHDSI study locally, the data never leaving the machine.

02Background & objective

The IPCOR registry

IPCOR is Ireland's national prostate-cancer registry. It captures the diagnostic work-up, staging, pathology, treatment and follow-up of men assessed for prostate cancer across a network of participating hospitals. The data is rich and clinically detailed, but held in the registry's bespoke structure and coding, which makes cross-study analysis difficult without standardisation.

Why OMOP

The OMOP Common Data Model is the open standard maintained by the OHDSI community for observational health data. Once data is in OMOP, standard analytical tools and study packages run against it unchanged, and results can be compared or pooled across institutions. A registry with no existing standard vocabulary cannot simply be relabelled: every field and coded answer must be matched to a standard concept drawn from the OMOP vocabularies (SNOMED, LOINC, RxNorm and others), downloaded from Athena. That concept-matching, and the review that goes with it, is the heart of this work.

The wider vision, a federated network

The end goal is a federated model: IPCOR becomes a node in an OMOP network where researchers send their analysis as code, the code runs locally against the OMOP data, and only aggregate results leave the machine. The raw records never move. Standardising IPCOR to OMOP is the enabling first step, and the analysis workbench below is where such external studies would run.

03The source data

The extract is five CSV files that together describe each patient's prostate-cancer pathway, linked by a single pseudonymised patient identifier.

Source fileWhat it records
demo-diagnosis.csvDemographics and the diagnosis record: age, PSA, Gleason/ISUP grade, clinical T/N/M stage and TNM group, risk scores (NCCN, CAPRA, PRIAS), histology, staging-imaging flags, smoking and family history.
sub-form.csvThe longitudinal follow-up: the PSA series (repeated readings with dates) and MRI (PI-RADS, prostate volume and dimensions).
biopsy.csvBiopsy records: date, approach, Gleason, laterality, detection basis and the tumour-present outcome.
treatment.csvSurgery, radiotherapy, ADT, chemotherapy, brachytherapy, watchful waiting and active surveillance, with intent and stop reasons.
proms.csvPatient-reported outcomes (EPIC-26 and related instruments).

Cohort. The extract references 302 patients; the built CDM holds 300 (two out-of-cohort records are excluded by configuration, never by editing the source). Conventions the mapping honours exactly include: grade recorded as numbers (ISUP 1-5 with -1 as a "not assessed" sentinel; NCCN a 1-5 ordinal; PRIAS 0/1; CAPRA 0-10); stage fields carrying the crosswalk's description text; and PSALevel being a positional index into the PSA sub-form series (which PSA test the record points to), not a PSA value, so the canonical numeric PSA is the sub-form series itself.

The extract is a mid-compilation snapshot of a live registry, so some fields are legitimately incomplete rather than wrong, missingness often reflects a reporting schedule or a benign patient who correctly has no diagnosis. This maturation-versus-error distinction runs through the Q&A.

05How the mapping was done, the OHDSI methodology

Because IPCOR has no vocabulary of its own, the central activity was finding and reviewing a standard concept for every field and value, using Athena and Usagi.

StepToolWhat was produced
1 · Profile the sourceWhiteRabbitA scan report of every table, field, data type, and the distinct values and frequencies, the basis for all decisions.
2 · Design the ETLRabbit-in-a-HatA table-by-table mapping specification, authored collaboratively with one owner per target table.
3 · Field-level mappingAthenaFor each variable, the standard concept describing what it records (Standard = "Standard"; follow "Maps to" where needed).
4 · Value-level mappingUsagi + AthenaFor each categorical answer, its standard concept, mapped and reviewed in Usagi, exported as a source-to-concept map.
5 · Load & transformPython ETLThe finished crosswalks load; the transformers build the CDM, the eras, visits, observation_period and the alignment steps.
6 · ValidateOHDSI DQDAutomated conformance, completeness and plausibility checks over the built CDM.

The full Rabbit-in-a-Hat design, every source column mapped to its OMOP table and field with the logic and modelling notes, is provided as a companion document, the IPCOR OMOP Field-Level Mapping Specification (bundled with this documentation). This page covers the method and the decisions; that specification is the detailed field-by-field reference behind them.

Field-level versus value-level

Two distinct levels of mapping were needed, and keeping them separate is what makes the result correct. Field-level is what a variable records (an EPIC-26 question maps to a concept for that question); these decisions live in the per-file variable maps. Value-level is what a particular answer means ("About once a week" maps to its own concept, stored as value_as_concept_id); these are made in Usagi.

Mapping conventions

  • Standard concepts only, where the best match is non-standard, follow its "Maps to" relationship.
  • Domain must match the table, a Condition concept is not used in an Observation or Measurement row.
  • concept_id = 0 is a last resort, with the original value kept in the source-value field.
  • Absence is not a row, the absence of a condition is the absence of a record, not a "No" row.
  • The source CSVs are the single source of truth, loaded tables are never hand-edited.

After the clinical tables load, builders run automatically: visits are grouped from event dates; observation_period is each patient's first-to-last span; condition and drug eras roll up on the 30-day gap rule; and fact relationships record the documented links. Two idempotent alignment steps then re-code TNM staging to the AJCC/UICC Cancer Modifier concepts network studies expect, and the watchful-waiting/active-surveillance observations to their per-value concept.

07What was not mapped, and why

Being explicit about what is not yet mapped is part of an honest hand-off. Nothing below is an error; each is a deliberate, documented decision.

ItemWhy it is not mapped (yet)
Patient-reported outcomes (proms.csv)The baseline EPIC-26 value set is mapped in Usagi (the worklists exist), but the PROMs transformer is not yet wired into the pipeline. Only the baseline survey carries data; demographics and 6-month follow-up are empty and map when data arrives.
Pointer / index fieldsFields such as the diagnosis PSA-level pointer are positional indices into a series, not values; not mapped to a concept by design.
Fields awaiting an IPCOR value crosswalkA few treatment values (and cause of death) are kept as source strings and resolve once IPCOR confirms their value list.
Fields absent from the extractA few dictionary fields are not yet in the extract and are pre-wired to populate when supplied (for example the ADT primary-or-salvage and stop-reason fields). ADT dose is not collected by the registry at all. The surveillance-type field and the specific ADT agent and dates are present and are mapped.
No-suitable-concept fieldsWhere no standard concept fits, the value is kept with concept_id = 0 and the original preserved, rather than forcing a misleading concept.

08Keeping the mapping faithful to the source

Keeping the mapping close to what the registry actually means, not just what the data superficially looks like, was a governed, iterative process.

The review loop. Every mapping passed through the same loop: profile the source (WhiteRabbit) so decisions rest on real values; design the target in Rabbit-in-a-Hat, table by table, with a named owner; map field- and value-level against Athena/Usagi; review each decision (standard concept, correct domain, sensible target); load; and validate with the DQD. Ambiguities were not guessed, they were escalated to IPCOR and resolved before being baked in.

  • Standard-concept checking, a validation step confirms every mapped concept is a standard OMOP concept.
  • Unmapped-column coverage, a report lists which source columns are and are not mapped, so nothing is silently dropped.
  • OHDSI Data Quality Dashboard, the community-standard conformance/completeness/plausibility battery, surfaced on demand in the mapper.

09Clarifications with IPCOR that shaped the mapping

Where the source data alone could not settle a modelling question, it was put to the IPCOR team and answered. Each point below is shown with IPCOR's clarification and the mapping decision that followed. These are what keep the mapping close to the registry's intent.

Point raised with IPCORIPCOR’s clarification and how it shaped the mapping
When and where smoking status and family history are recorded.IPCOR confirmed these are in the demographic form and are noted at the biopsy, so they are dated from the date of biopsy (which every patient has) rather than the diagnosis date. This keeps them for the negative-biopsy patients, who have a biopsy but no diagnosis.
Which MRI, PSA and facility record is authoritative when the same item appears in several forms.IPCOR confirmed the real values live in the sub-forms, and the versions in the diagnosis, biopsy and treatment forms are drop-down selections pointing to those sub-form values. The sub-form is therefore the authoritative source. MRIs sharing a date and PI-RADS are treated as duplicates and removed; a missing date or result means the value is genuinely unavailable.
Whether ISUP and NCCN can be mapped to code lists, and what the value -1 means.IPCOR confirmed ISUP and NCCN are calculated grade-group and risk scores, so there is no code list to map to and they are kept as numeric scores. A value of -1 means the score could not be calculated because a required input was missing, so it is stored as missing.
The one patient whose diagnosis record is internally contradictory.IPCOR confirmed this is a known system glitch in which a diagnosis date could not be removed, and the patient is negative. The record is treated as benign and the stray date is disregarded.
What the numeric facility codes mean.IPCOR confirmed the numeric code is the index of the institute in the Institute sub-form (1 is the first institute, 2 the second, and so on), so the facility is resolved from the sub-form and the codes are read as positional pointers. The Hospital and Institute names are pseudonyms, so each real facility maps to one care_site.
What the biopsy MRIDetails code represents.IPCOR confirmed it is the index of the MRI scan in the MRI sub-form (1 is MRI 1, 2 is MRI 2), so it is a positional pointer into the sub-form rather than a clinical result, and is not mapped as a concept.
Whether PSALevel is a PSA value or a code.IPCOR confirmed PSALevel is the index of the PSA test in the PSA sub-form (1 is PSA 1, 2 is PSA 2), so it is a positional pointer, not a PSA value. The canonical numeric PSA is taken from the sub-form, and PSALevel is not mapped as a measurement.
Whether active surveillance and watchful waiting can be told apart in the extract.The surveillance-type field (WWASType) was not in the first requested variable list but is present in the current extract. Active surveillance and watchful waiting are recorded distinctly (73 and 6 records) and map to separate standard concepts, each with its date and treating clinician, so the two are not collapsed.
Whether the specific ADT agent and the ADT dates are available.The ADT agent and dates were not in the first requested variable list but are present in the current extract. The specific agent (for example bicalutamide, relugolix or triptorelin) is recorded and maps to a standard drug ingredient in DRUG_EXPOSURE, with the start and stop dates; agents recorded as "Other" are kept as the source value. ADT dose is not collected by the registry, so no dose is recorded.
Whether radiotherapy delivered at specialist centres is captured.IPCOR confirmed that care delivered at non-recruiting sites, including St. Luke's radiation-oncology network, is captured, with the treating facility recorded in each treatment form. Radiotherapy is therefore not under-recorded because of site coverage.

Several further decisions were confirmed with the registry and are in the code: visit-date semantics (treatment and biopsy dates are real attendance, while PSA and MRI dates are result-recorded and approximate), instance ordering (entry order, not chronological, so records are sorted by date), a diagnosis-date definition change handled by a cutoff rule, the 300 versus 302 cohort exclusion by configuration, and a few confirmed real-world column-name variants.

10How to run the pipeline

There are two ways to run it; both keep the patient data on the local machine.

The turnkey appliance (recommended)

A sealed, double-click deployment requiring only Docker Desktop. Unzip the starter package and double-click Start; a browser opens the mapper. No repository, no code, no login, the images pull from a public registry on first run.

  • Start → the mapper opens.
  • Map & build → upload the five CSVs, validate, click Build, download the OMOP tables.
  • Explore → the dashboard (overview, pathways, cohort builder, query builder, SQL console) opens alongside.
  • Analyse with code → double-click Start-research for RStudio Server and JupyterLab, preconnected to the CDM.
  • Stop / Update → Stop keeps the database; Update pulls the newest image.

The developer route

The same pipeline runs from the repository: a PostgreSQL database with the vocabulary loaded, the Python ETL in stages (staging → vocab → cdm) with the derived tables built automatically, the R steps for observation_period and the DQD, and the Dash dashboard over the result.

The research workbench

This is where an external OHDSI study runs against the data. RStudio Server is the native home for an R study package; JupyterLab offers the same connection in Python or R. Both read the connection from the environment, so a researcher opens a seeded script and runs it with no configuration. Because they execute arbitrary code against the CDM, they are login-gated, and any external study package is reviewed before it is run.

11Data quality & known limitations

The built CDM passes the OHDSI Data Quality Dashboard's checks, which can be re-run on demand from the mapper. Limitations worth stating plainly:

  • ADT dose is not collected by the registry (there is no dose field); the ADT agent, start date and stop date are captured and the agent maps to a standard drug ingredient, so dose is the only ADT attribute unavailable (Q&A 9).
  • A few coded values have no exact standard concept and are kept as the source value with concept_id = 0 (for example ADT agents recorded as "Other"), rather than forcing a misleading concept.
  • Baseline characteristics (smoking, family history) are dated from the biopsy date, the assessment point IPCOR confirmed; a methods point for time-based analysis (Q&A 1).
  • The extract is a mid-compilation snapshot; some missingness is maturation, not error, and flagged records will be re-dated when IPCOR supplies a single synchronised extract.
  • Patient-reported outcomes (the PROMs form) are not mapped in this release.

None of these are defects in the mapping; they are properties of the current source extract, documented so analysis is interpreted correctly.

12Synthetic data for safe testing

So collaborators can develop and test analysis code before any real data is involved, the pipeline includes a synthetic-cohort generator. It produces a clinically coherent prostate-cancer cohort in the exact IPCOR source format, from the structure and the mapping vocabularies alone, it never reads the real data. Each synthetic patient is simulated from clinical priors, so no row corresponds to a real person, and the cohort is built to mirror the concept coverage of the real CDM, so code that runs against the synthetic data will run against the real data. A collaborator builds and tests their study on the synthetic cohort on their own machine; only the finished code is later run against the real data locally.
